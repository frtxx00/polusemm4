========================================================================
Скрипт фильтрации аномальной активности респондентов (Data Cleaning Pipeline)
========================================================================

Суть и назначение кода:
-----------------------
Этот скрипт очищает сырые медиаданные (из Parquet-файлов) от "накруток", бот-активности и аномального поведения отдельных пользователей. Он находит респондентов, которые совершают неестественно много действий в рамках одного бренда и категории за день (генерируют слишком большой OTS), и временно исключает их вклад, чтобы не искажать общую статистику.

Алгоритм работы (как это устроено внутри):
-------------------------------------------
1. Сбор данных: Скрипт собирает все файлы во входной папке, фильтрует только нужные целевые записи и приводит типы данных к общему стандарту.
2. Расчет метрик активности: Для каждого пользователя за каждый день рассчитывается его доля (share) в общем объеме бренда, отклонение от нормы (deviation) и устойчивость такого поведения во времени (persistence).
3. Скоринг и поиск аномалий: На основе комбинации этих метрик вычисляется финальный "балл подозрительности" (score). Если балл превышает критический порог (99.5-й квантиль), респондент за этот день помечается как аномальный. Скрипт учитывает общие рыночные инфоповоды (events), чтобы случайно не наказать честных людей во время крупных медиа-событий.
4. Очистка данных: Применяется каскадное удаление. Если пользователь совершил аномальные действия по какому-то бренду, его вес (Weight) за весь этот день зануляется.
5. Аналитика и графики: Скрипт сохраняет очищенный массив, логи с причинами блокировок, а также строит графики сравнения "До/После" (по дням, категориям и брендам), чтобы наглядно показать качество очистки.

Что вы получаете на выходе:
---------------------------
В папке output/ появятся:
* cleaned_data.csv — Очищенный датасет, готовый для финальной аналитики и отчетов (веса аномальных дней занулены).
* anomalies.csv — Простой список пар [Пользователь + Дата], которые были признаны подозрительными.
* anomaly_reasons.csv — Подробный отчет с причинами блокировки (конкретные метрики и баллы нарушителей).
* plots/ — Наглядные графики, демонстрирующие, как ушли экстремальные пики и как изменились показатели.

В самом конце работы скрипт выведет в консоль финальные метрики эффективности: какой процент базы отсеялся и насколько удалось сгладить аномальные всплески.

более подробно по этапам:

1. Загрузка и подготовка данных
Ищет все файлы *.parquet в input_data/ во всех подпапках (ваши 5 месяцев).
Склеивает их в одну таблицу df_old.
Оставляет только строки с BrandinDelivery = 1 (в поставке SoS).
Работает с категорией CategoryNameDelivery (в ваших файлах так названа колонка категории поставки).
Приводит researchdate к дате, Weight к числу, убирает пустые даты и веса.
Итог: одна большая таблица «сырых» запросов для анализа.

2. Агрегация до уровня «респондент – бренд – категория – день» (build_features)
Группировка: SubjectID, researchdate, BrandID, Brand, CategoryNameDelivery.

Для каждой группы считается:

Поле	Как
count_rows
Сколько строк-запросов у этого человека к этому бренду в этот день
Weight
Дневной вес респондента (берётся один раз, first)
daily_ots
count_rows × Weight — вклад человека в OTS бренда за день
Потом для каждого дня + бренда + категории (без SubjectID):

Поле	Как
brand_day_ots
Сумма всех daily_ots по бренду за день (общий OTS бренда)
unique_users
Сколько разных респондентов было у бренда в этот день
Эти поля подмешиваются к каждой строке респондента — чтобы сравнивать человека с «фоном» бренда в тот же день.

3. Доля респондента в бренде (add_share)
Сглаженная доля (чтобы мелкие бренды не давали ложных пиков):

share = (daily_ots + α) / (brand_day_ots + α × unique_users)
У вас α = 10 — небольшое «приоритетное» сглаживание: при малом числе пользователей доля не улетает в 0 или 100% из-за шума.

Смысл: какую часть OTS бренда за день «забрал» этот респондент.

4. Отклонение от «равной доли» (add_deviation)
Если бы все unique_users делили бренд поровну, у каждого была бы доля:

expected_share = 1 / unique_users
Отклонение:

deviation = share / expected_share
deviation ≈ 1 — как у «среднего»
deviation >> 1 — человек взял больше, чем если бы делили поровну
Смысл: насколько вклад непропорционален числу людей в бренде за день.

5. Устойчивый z-score внутри дня (robust_z)
Внутри группы researchdate + BrandID + CategoryNameDelivery по всем респондентам считается для daily_ots:

robust_z = (daily_ots − медиана) / (MAD + ε)
MAD — медианное абсолютное отклонение (устойчивее обычного std к выбросам).

Смысл: насколько абсолютный OTS человека выбивается среди всех в этот день в этом бренде (не только доля, но и масштаб).

6. Дни «рыночного всплеска» бренда (add_event)
Для каждого дня, бренда, категории:

total = суммарный brand_day_ots (OTS бренда за день).
Сортировка по бренду и дате.
baseline = медиана total за предыдущие 7 дней (скользящее окно, минимум 3 дня истории), отдельно по каждому BrandID.
growth = total / (baseline + 1) — во сколько раз сегодня выше «нормы» бренда.
Порог по всей истории: 99.5-й перцентиль growth.
is_event = True, если growth выше этого порога.
Смысл: в такие дни бренд мог вырасти у всех, и не хочется считать аномалией каждого активного пользователя.

(В коде baseline считается по BrandID, без разбивки по категории внутри groupby — это особенность вашей реализации.)

7. «Повторяемость» респондента (persistence)
activity_days = сколько раз этот SubjectID встречается в агрегированной таблице (сколько бренд-дней у человека в данных).
persistence = deviation × log(1 + activity_days).
Смысл: человек с частой активностью и высоким deviation получает больший вклад в итоговый риск, чем разовый всплеск у редкого респондента.

8. Итоговый score (add_score)
Каждый из четырёх признаков переводится в ранг от 0 до 1 по всей выборке (rank(pct=True)):

deviation_rank
robust_rank
share_rank
persistence_rank
Score — взвешенная сумма:

Признак	Вес
deviation
40%
robust_z
25%
share
15%
persistence
20%
Смысл: одна числовая «подозрительность» из разных углов; ранги снимают проблему разных масштабов между брендами.

9. Порог и флаг аномалии
base_thr = 99.5-й перцентиль score по всей выборке (верхний хвост).
threshold = base_thr × 1.05, если для этой строки is_event, иначе base_thr.
is_anomaly = True, если score > threshold.
Смысл: режете не «N% людей руками», а самые высокие составные скоры; в дни всплеска бренда планка чуть выше.

10. Каскадное удаление (как в задании)
Из всех строк с is_anomaly берутся уникальные пары (SubjectID, researchdate) → anomalies.csv (только эти 2 колонки).
В anomaly_reasons.csv — все срабатывания по брендам с полями: бренд, daily_ots, score, threshold, reason (строка с числами: daily_ots, share, deviation, robust_z).
В df_cleaned: если пара (человек, день) в списке аномалий → Weight = 0 для всех строк этого человека за этот день (все бренды и категории).
Смысл: триггер по бренду, удаление — за весь день.

13. Метрики в конце скрипта
Считаются для самопроверки:

Доля респондентов, у которых все дни с нулевым весом (фактически выбыли из «активных»).
% потери суммарного OTS.
Максимальный пик OTS на паре (день, BrandID) до и после.
(опционально) TOP-20 пиков по (день, Brand).
Схема потока (кратко)
parquet (5 месяцев)
    → фильтр BrandinDelivery
    → daily_ots по человеку/бренду/дню
    → share, deviation, robust_z
    → is_event (всплеск бренда)
    → persistence
    → score (4 ранга)
    → порог 99.5% (+5% в event)
    → anomalies + reasons + cleaned_data + графики
